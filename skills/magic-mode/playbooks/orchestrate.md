# Orchestrate

**You run the program, never the code. Decide which agent does each piece of work, then check what each one produces.** For a standing project handed to one coordinator chat, multi-day, many stacked PRs, dozens to hundreds of subagents, few human turns. One task driven to a predicate is Autonomous run. One ambitious run that needs a bespoke workflow is figure-it-out. Work that one agent could finish inside the session's budget is not a program.

Run it with your own tools. Spawn workers with the subagent tool, and resolve every spawn's model from a role line in the `magic-models` role file. Keep the program's state in the Project tracker (`notes.md`) and the Project store. Watch each PR with PR and CI event subscriptions when your harness has them. Call no scripts, run no polling loops, and never relay messages or status between agents.

## Topology

- **Default to a flat two-level topology.** This chat is the coordinator at depth 0, and every owner, verifier, and auditor is a leaf `magic-agent` at depth 1, partitioned in `notes.md` before the first spawn. One row per lane names its files, its owner, and its verifier. That partition is the topology, and a leaf never spawns a subagent, because the supported harnesses stop at depth 1.
- **A sub-coordinator only when the harness explicitly supports `depth >= 2`.** Then, and only then, one area with many parallel workers may get a sub-coordinator that owns its workers and kickoffs and sends this chat one rollup instead of raw reports. Stop at three levels in that case, this chat, sub-coordinators, and workers. Keep about ten workers in flight per coordinator, and start the next one as each finishes instead of waiting on a whole batch. On a depth-1 harness the answer is more lanes here, never a nested coordinator.
- **One owner per PR.** The owner is the only writer of its branch and carries the PR from build to merge. Bind it to the `feature, refactoring` line (default `main`), or to `hardest tasks` (default `deep`) for cross-cutting design, gnarly concurrency, and subtle algorithms. Only the owner pushes, rebases, or retargets it. Closing or retargeting a base PR orphans every PR above it, so the owner does that only on your call. You never author or edit code. Conflicted merges, chain rebases, and fixes go to owners.
- **A fresh worker for each independent task.** Its kickoff carries everything it needs, including each upstream report it depends on, pasted in full. Workers can't see their siblings. Run workers as isolated-worktree subagents unless the work needs this machine, runtime verification through the project's verification skill (`verify-<app>`, generated by the **create-verification-skill** skill) or the harness's browser or CLI driving tools, local transcripts, a simulator, or auth that exists only here. Pick each subagent's reasoning level and fast or standard speed for the job, per the Subagents section.
- **Fork when new work needs a worker's built state,** such as its checkout, uncommitted changes, or a running process. Message a worker only for a follow-up on the same work. Never message one to check on it, because a message restarts an idle agent.
- **Each PR gets a verifier that isn't its author.** Dispatch it on the `swarm workers` line (default `main`), or on the `arena cross-judge pool` (default `deep`) for a cross-family seat, preferring a family different from the parent chat's. The owner merges only on that verifier's pass at the current head.
- **Run the review wave from this chat at `code-ready`.** This chat dispatches `comment-sicko` at depth 1, alongside the verifiers, so a PR owner never nests the comment audit. The owner reports `code-ready`, and this chat dispatches `/no-comments` and the `swarm` verifiers as separate leaves.
- **Start with one unit.** Take it through kickoff, owner, verifier, and merge before you fan out, so a flaw in the kickoff costs one agent instead of fifty. On near-identical cheap units, the first unit is that test.

## Supervision

- **Each kickoff names the evidence that proves the work is done,** such as a command and its expected output, a verification-skill check, or an artifact. It also names the goal, the paths the worker may and may not write, and the actions it must not take. If you can't name the evidence, the unit isn't scoped yet.
- **Read the diff or the artifact, not only the worker's summary.** Green CI is an input to a verdict, not a verdict. Behavioral work needs more than a type check. A verdict covers one head SHA, so a new push needs a new verdict. Read a sample of each lane brief while its workers run, and fix the instructions when one fails.
- **Send back work that drifts from scope or grows past what was asked.** Keep only the fixes that block the program, and park the rest as follow-ups.
- **Check a PR's live state before you report on it,** using the forge operations **view PR** and **list checks**, not the worker's last report. Account for every worker you spawned as done, replaced, or absorbed into another worker's scope.
- **Stop or replace a worker that stalls or loops.** Judge it by its pushes and PR activity, not its status text. Retry by cause, a smaller scope after a context or memory limit, the same kickoff after a dropped connection, and a different model after a tool error. After two retries, drop the unit and replan around it. When a stopped worker returns late, check its result against the PR's current state, and hand any unique findings to a fresh worker.
- **Ask the user only for a real decision or a blocker,** such as an irreversible action, a product or preference call that no experiment settles, or a dead end that survived a replan. Rebase mechanics, retries, CI flakes, review triage, and "should I keep going" never reach the user.

**Reply.** State what landed against the goal, each PR's live state and verdict with its link, what was dropped and why, and the decisions waiting on the user.
